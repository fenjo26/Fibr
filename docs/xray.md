# Xray (VLESS) — второй протокол

WireGuard — основной протокол Fibr: быстрый, встроен в ядро, работает на
роутерах и телевизорах. Но его рукопожатие хорошо видно системам анализа
трафика (DPI), и в ряде сетей его блокируют. Для таких сетей у Fibr есть
второй протокол — Xray с транспортом VLESS + Reality: он маскируется под
обычный HTTPS-трафик к крупному сайту.

Выбор протокола — на уровне устройства: один пользователь может иметь и
WG-устройство (телефон), и Xray-устройство (ноутбук в закрытой сети).

## Два транспорта: XHTTP на 443 (основной) и Reality (запасной)

У одних и тех же VLESS-клиентов (один UUID на устройство) два входа:

| | XHTTP + TLS (основной) | Reality (запасной) |
|---|---|---|
| Адрес в ссылке | `ваш-домен:443` | `IP/домен:FIBR_XRAY_PORT` (8443) |
| TLS | настоящий сертификат вашего домена (Caddy) | маскировка под `FIBR_XRAY_SNI` |
| Как выглядит для провайдера | обычный HTTPS к вашему сайту — тот же трафик, что у кабинета и мини-аппа | TLS к «microsoft.com» на нестандартном порту чужого IP |
| Где работает | на этом сервере (за Caddy) | этот сервер и ноды мультинода |

**Зачем.** В России ТСПУ видит, что Reality-соединение на 8443 «притворяется»
microsoft.com, хотя IP не майкрософтовский: рукопожатие проходит, а данные
обрываются («подключается, но не работает»). При этом HTTPS к самому
домену Fibr проходит — кабинет и мини-апп открываются. XHTTP прячет VLESS
именно в этот трафик: Caddy принимает TLS на 443 своим сертификатом и
проксирует секретный путь (`FIBR_XHTTP_PATH`) во второй inbound xray
(`vless-xhttp`, порт 10086 внутри compose-сети, наружу не опубликован).
Всё остальное на домене работает как раньше.

Ссылка устройства выглядит так:

```
vless://UUID@vpn.example.com:443?encryption=none&security=tls&sni=vpn.example.com&fp=chrome&alpn=h2&type=xhttp&host=vpn.example.com&path=%2F<секрет>&mode=auto#Fibr-phone
```

Её понимают актуальные Hiddify, v2rayNG, v2RayTun, Streisand,
Happ (транспорт `xhttp` есть в Xray-core с конца 2024 года — приложение
должно быть обновлено).

Условия — выполняются сами:

- `FIBR_DOMAIN` — настоящий домен с HTTPS (не `http://localhost`, не IP);
- `FIBR_XHTTP_PATH` в `.env` — случайный путь, `install.sh` дописывает его
  сам; Caddy читает то же значение (без него у обоих стоит `/fibr-xh`).
  **Не меняйте путь после выдачи ссылок** — он внутри каждой ссылки;
- выключить XHTTP: `FIBR_XHTTP_ENABLED=false` (ссылки снова станут Reality).

Реальный IP клиента Caddy передаёт в `X-Forwarded-For`, xray доверяет ему
(`sockopt.trustedXForwardedFor`), поэтому лимитер «одна ссылка — одно
устройство» работает и для XHTTP.

**Обновление уже работающего сервера** (старые VLESS-ссылки перестанут быть
основными — пользователям нужно заново взять ссылку/QR в кабинете):

```bash
cd /opt/fibr && git pull
grep -q '^FIBR_XHTTP_PATH=' install/.env || echo "FIBR_XHTTP_PATH=/$(openssl rand -hex 8)" >> install/.env
cd install && docker compose up -d --build
docker compose restart xray caddy
```

## Включение

**Xray включён по умолчанию** — ничего настраивать не нужно: каждый
пользователь сам выбирает протокол (WireGuard или VLESS) при создании
устройства в Mini App / кабинете, а в боте есть `/new` (файл WireGuard) и
`/vless` (ссылка VLESS). Ключи Reality и short id сервер генерирует сам и
хранит в базе, SNI по умолчанию — `www.microsoft.com`.

Нужно только открыть в файрволе TCP-порт `FIBR_XRAY_PORT` (по умолчанию
8443), если файрвол активен (`install.sh` делает это сам для ufw).

Необязательные настройки в `/opt/fibr/install/.env`:

- `FIBR_XRAY_SNI=<домен маскировки>` — большой сайт с TLS 1.3 + HTTP/2,
  желательно географически близкий к вашему серверу (не свой домен);
- `FIBR_XRAY_PORT=443` — если 80/443 свободны от Caddy на отдельном IP;
- `FIBR_XRAY_ENABLED=false` — выключить VLESS совсем (и `docker compose
  stop xray`).

Старый сервер, где в `.env` записано `FIBR_XRAY_ENABLED=false`, включается
так:

```bash
cd /opt/fibr/install
sed -i 's/^FIBR_XRAY_ENABLED=.*/FIBR_XRAY_ENABLED=true/' .env
docker compose up -d --build
```

Ключи Reality генерируются самим сервером и хранятся в базе — вручную ничего
создавать не нужно.

## Клиенты

QR-код Xray-устройства содержит ссылку `vless://…`. Её понимают:

- **Android:** v2rayNG, Hiddify
- **iOS:** Streisand, Hiddify, v2RayTun, Happ
- **Windows/macOS/Linux:** Hiddify, Nekoray, v2rayN

В миниаппе и админке при создании устройства просто выберите протокол Xray —
QR и текст ссылки доступны там же, где и обычные WireGuard-конфиги.

## Ограничения MVP

- **Нет статистики**: трафик и «онлайн» для Xray-устройств не считаются
  (показываются нули). WireGuard-устройства считаются как обычно.
- **Применение изменений** — теперь на лету: конфиг включает gRPC API xray
  (порт 10085, только внутри compose-сети, наружу не публикуется), и fibr
  добавляет/удаляет клиентов через него сразу. Файл
  `/data/xray/config.json` по-прежнему перезаписывается, так что
  перезапуск контейнера всегда приводит к тому же состоянию. **Один раз
  после обновления** перезапустите xray, чтобы он поднял API:

  ```bash
  docker compose -f /opt/fibr/install/docker-compose.yml restart xray
  ```

  Отключить живое применение: `FIBR_XRAY_API=off` (тогда снова нужен
  перезапуск после изменений, а лимитер не работает).

## Одна ссылка — одно устройство (лимитер)

VLESS-ссылка — статичный секрет, привязать её к телефону в самой ссылке
нельзя. Поэтому сервер смотрит, **откуда** ссылкой пользуются: xray пишет
access-лог (`/data/xray/access.log`) с UUID ссылки и IP источника, fibr
считает разные IP на каждую ссылку и, если их больше лимита, временно
отключает именно эту ссылку и пишет владельцу и админам в бот.

| Переменная | По умолчанию | Смысл |
|---|---|---|
| `FIBR_XRAY_IP_LIMIT` | `2` | сколько разных IP одновременно разрешено на ссылку; `0` — без лимита |
| `FIBR_XRAY_IP_WINDOW` | `2m` | сколько «помнится» увиденный IP |
| `FIBR_XRAY_BAN` | `10m` | на сколько отключается ссылка при превышении |
| `FIBR_XRAY_API` | `xray:10085` | адрес gRPC API xray; `off` — выключить |

Лимит считает **сети, а не телефоны**: телефон при переходе Wi-Fi → LTE
пару минут виден с двух IP (поэтому по умолчанию 2), а несколько людей за
одним роутером выглядят как один. От перепродажи одной ссылки десяткам
людей это защищает. Жёстче всего ограничивает WireGuard/AmneziaWG: один
файл на двух устройствах одновременно просто не работает.

- Reality-советы из логов xray: маскировка под «www.microsoft.com» и работа
  на нестандартном порту повышают шанс блокировки IP в агрессивных сетях —
  поэтому основным транспортом стал XHTTP на 443 (см. выше); Reality
  остаётся запасным и для нод мультинода.
