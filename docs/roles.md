# Роли: superadmin, admin, user (reseller-иерархия)

В Fibr три роли. Модель закрывает сценарий «владелец продаёт/раздаёт VPN через
реселлеров»: суб-админ ведёт своих людей сам и не видит чужих вообще.

| | superadmin | admin | user |
|---|---|---|---|
| Кто это | владелец инсталляции | суб-админ / реселлер | конечный аккаунт |
| Как становится | статический `FIBR_ADMIN_TOKEN` или telegram-id из `FIBR_ADMIN_TELEGRAM_IDS` | назначается superadmin'ом в панели | регистрируется сам (или создаётся админом) |
| Видит пользователей | всех | только созданных им (`owner_id`) | — |
| Видит устройства | все | своего subtree (свои + пользователей) | свои |
| Создаёт пользователей | `user` и `admin` | только `user` (автоматически «свои») | — |
| Меняет роли | да | нет (403) | — |
| Отключает/удаляет | любого | только своих | — |
| `GET /api/admin/overview` | да | **403** (не его метрика) | — |
| Приглашения (панель, бот, `/invite`) | все | только свои | — |
| `/stats` у бота | да | нет | нет |
| Вход в админ-панель | да (это и есть панель) | **нет** | нет |

## Кто видит что

- **superadmin** — всё: всех пользователей, все устройства, общую статистику,
  все приглашения. Это статический токен `FIBR_ADMIN_TOKEN` (вход в панель) и
  все telegram-id из `FIBR_ADMIN_TELEGRAM_IDS`: при первом входе через Mini App
  такой аккаунт создаётся сразу с ролью `superadmin`, а существующий аккаунт с
  ролью `admin` из этого списка будет автоматически повышен при следующем
  входе.
- **admin** — только свой «subtree»: пользователи, у которых `owner_id` равен
  его id, и их устройства. Собственные устройства админ по-прежнему видит в
  Mini App через `/api/me`. Чужие сущности отвечают **404** — админ даже не
  может определить, существует ли id. В `GET /api/admin/users` самого админа
  в списке нет (только его пользователи).
- **user** — только свои устройства, QR и своя статистика. Ему в Mini App
  секция «Пользователи» не показывается вовсе.

## Кому что доступно в API

Bearer для `/api/admin/*` — статический токен (superadmin) или сессия
пользователя с ролью admin/superadmin.

| Endpoint | superadmin | admin |
|---|---|---|
| `GET /api/admin/users` | все | только свои (`owner_id = его id`) |
| `POST /api/admin/users` | role `user`/`admin` (owner — он сам) | только `user`, owner принудительно он; попытка создать `admin` → 400 |
| `PATCH /api/admin/users/{id}` | роль и disabled кому угодно | только своим: `disabled`; `role` → 403; чужие → 404 |
| `DELETE /api/admin/users/{id}` | любой | только своим (устройства каскадом); чужие → 404 |
| `POST /api/admin/users/{id}/devices` | любому | только своим; чужие → 404 |
| `GET /api/admin/devices` | все | устройства своего subtree |
| `PATCH/DELETE /api/admin/devices/{id}`, `/config`, `/qr.png` | любые | только subtree; чужие → 404 |
| `GET /api/admin/overview` | 200 | **403** |
| `GET /api/admin/invites` | все | только свои (`created_by`) |
| `POST /api/admin/invites` | да | да |
| `DELETE /api/admin/invites/{code}` | любой | только свой; чужой → 404 |

## Как повысить пользователя до админа

Админ-панель → **Пользователи** → напротив человека кнопка
**«Сделать админом»** (понизить обратно — «Сделать пользователем»). Рядом в
колонке **«Кто создал»** видно, чей это аккаунт (username создавшего).

Через API: `PATCH /api/admin/users/{id}` с `{"role":"admin"}` от имени
superadmin'а.

Повысить до superadmin через панель нельзя: эта роль приходит только из
`FIBR_ADMIN_TOKEN` / `FIBR_ADMIN_TELEGRAM_IDS`.

## Как дать суб-админу доступ

Никак через панель — вход в админ-панель только по статическому токену,
а он эквивалентен superadmin. Суб-админ работает целиком в **Mini App**:
пользователь с ролью `admin`, открыв приложение из бота, видит секцию
**«Пользователи»**:

- список своих людей: имя, Telegram, количество устройств;
- кнопка **«Выдать устройство»** — выбор протокола wg/xray, QR показывается
  сразу (можно передать человеку вживую);
- кнопка **«Приглашение»** — одноразовая ссылка, копируется одним нажатием.

Схема работы: superadmin повышает человека до admin → тот создаёт своих
пользователей (или раздаёт приглашения) → выдаёт им устройства и QR.

## Бот

- `/stats` — только superadmin (общая статистика инсталляции);
- `/invite` — admin и superadmin.

## Хранение

- `users.role` — `CHECK (role IN ('user','admin','superadmin'))`;
- `users.owner_id` — `INTEGER NULL REFERENCES users(id) ON DELETE SET NULL`:
  кто создал аккаунт.

SQLite не умеет менять CHECK на живой таблице, поэтому первое открытие базы
старой версии пересоздаёт таблицу `users` (create new → copy → drop → rename)
с сохранением всех строк, id и внешних ключей (`devices.user_id`,
`invites.used_by`). Миграция идемпотентна и выполняется один раз.

Если админа удалить или понизить, его пользователи остаются (полезный трафик
не рвётся): `owner_id` обнуляется, и ими дальше управляет superadmin.

## FAQ

**Можно ли создать superadmin в панели?**
Нет. Только `FIBR_ADMIN_TOKEN` и `FIBR_ADMIN_TELEGRAM_IDS` в
`/opt/fibr/install/.env` (потом `docker compose up -d`).

**Админ видит трафик всего сервера?**
Нет: `/api/admin/overview` отвечает 403, `/stats` у бота — отказ.

**Может ли админ «наугад» найти чужого пользователя по id?**
Нет: любые операции с чужим id отвечают 404, как будто его не существует.

**Что видит обычный пользователь в Mini App?**
Максимально простой экран: приветствие, свои устройства, QR с пошаговой
подсказкой (установить WireGuard → «+» → из QR-кода → отсканировать).

**Как узнать, кто чей?**
В панели — колонка «Кто создал»; в API — поле `owner_id` у пользователя.

**Приглашение, созданное админом, подселяет пользователя к нему?**
Нет: зарегистрировавшийся по ссылке — обычный пользователь без владельца.
«Своим» он станет, когда админ создаст аккаунт сам (или superadmin назначит
владельца). Приглашения нужны только как пропуск регистрации в режиме
`FIBR_REQUIRE_INVITE=true`.
