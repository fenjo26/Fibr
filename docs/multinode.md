# Мультинодовость: запасные серверы и быстрая подмена при блокировке

Один сервер = один IP, и IP рано или поздно блокируют. Fibr решает это
архитектурой **control plane + ноды**: основной сервер (тот, где админка,
бот и Mini App) остаётся мозгом, а VPN-трафик могут обслуживать
дополнительные машины — **ноды**. При блокировке вы просто делаете другую
ноду активной: все перевыгруженные QR/конфиги сразу указывают на новый
эндпоинт, а Mini App помечает устаревшие конфиги бейджем.

## Модель

- **Control plane** — основной сервер. База (SQLite), ключи, админка, бот,
  Mini App, выдача конфигов. Всегда первый в списке нод как **local**.
- **Нода** — любая дополнительная машина с двумя контейнерами: `fibr-node`
  (агент) и опционально `xray`. Нода не хранит пользователей: агент каждые
  20 секунд стягивает с control plane **полный список активных пиров**
  (только живые, неистёкшие устройства) и применяет их к своему
  WireGuard-интерфейсу. Статистику хендшейков/трафика агент отправляет
  обратно — «онлайн» и счётчики в админке работают как на основной машине.
- **Активная нода** — ровно одна на всю установку (глобально). Именно её
  адрес и публичный ключ попадают в выдаваемые клиентам конфиги и QR.
  Переключение мгновенное: смена активной ноды не трогает туннели — она
  меняет только то, что **рендерится** при следующем скачивании конфига.

У каждой ноды **своя** пара ключей WireGuard (и свои Reality-ключи для
Xray), поэтому в конфиге клиента меняются и `Endpoint`, и `PublicKey`
сервера — перекачать QR после переключения обязательно. Ключи **устройств**
при этом не меняются: устройство остаётся тем же пиром, работающим через
другую ноду.

Список пиров един для всех нод: любое устройство может подключиться к любой
ноде, но в выданном конфиге прописана активная.

## Кто управляет нодами

Только суперадмин — инфраструктура касается всей установки, реселлерам она
не видна (в админ-API ноды отдают 403 для роли admin).

## Добавление ноды

1. Панель → **Ноды** → **«Добавить ноду»**: имя и хост (IP или домен новой
   машины, A-запись должна уже указывать на неё), при необходимости порты.
2. Панель показывает **токен ноды** (один раз, сохраните) и готовый набор
   переменных для машины ноды.
3. На новой машине (Docker уже установлен):

   ```bash
   mkdir -p /opt/fibr-node && cd /opt/fibr-node
   # положите сюда docker-compose.node.yml из репозитория (install/)
   cat > .env <<EOF
   FIBR_API_URL=https://vpn.example.com
   FIBR_NODE_TOKEN=<токен из панели>
   EOF
   docker compose -f docker-compose.node.yml up -d
   ```

4. Агент при первом старте генерирует собственную пару ключей, регистрирует
   их на control plane, и нода в панели становится **готова** (`ready`).
   Через 20–30 секунд она уже обслуживает любых клиентов с любыми
   устройствами (если её адрес знает клиент — см. «переключение»).

Нода не требует домена с TLS: агент ходит в API основного сервера как
обычный клиент по HTTPS. UDP-порт WG (по умолчанию 51820) должен быть
открыт наружу; для Xray-нод — ещё и TCP-порт (по умолчанию 8443).

## Переключение при блокировке (runbook)

Ситуация: клиенты жалуются, нода молчит (в панели «offline» — нет отчётов
~70 секунд, либо хендшейки обнулились при живой ноде).

1. Панель → **Ноды** → у заблокированной ноды кнопка **«Заблокировать»**
   (статус `blocked`). Заблокированная нода получает от API пустой список
   пиров и перестаёт обслуживать трафик.
2. У запасной ноды кнопка **«Сделать активной»**. Моментально меняется
   эндпоинт всех будущих QR.
3. Пользователи перекачивают конфиг: в Mini App у каждого устройства
   появится бейдж **«конфиг устарел»** — нажать «QR-код»/«Конфиг» заново и
   пересканировать. Клиент Fibr (этап 2) узнаёт свой конфиг по ключу
   устройства (он не меняется при подмене ноды) и предлагает **обновить
   туннель на месте** вместо дубля; официальные WireGuard-клиенты —
   удалить старый туннель и добавить по новому QR.
4. Разблокировать/заблокировать обратно можно в любой момент (кнопка).

Бейдж «конфиг устарел» появляется, когда нода стала активной (или у активной
ноды изменили адрес/порт) **после** последнего скачивания конфига этим
устройством. Бейдж не знает, успел ли клиент применить конфиг, — это
подсказка, а не гарантия.

## Что видно в панели

- **Ноды**: имя, хост, статус (`готова` / `ожидает` / `заблокирована`),
  онлайн (по последнему отчёту агента), количество пиров, метка «активная».
- Дашборд: адрес и имя активной ноды.
- `GET /api/admin/nodes` — то же самое в JSON (токен не отдаётся никогда,
  только при создании).

## Ограничения (честно)

- **Активная нода одна на всех** — индивидуальных нод на пользователя/ветку
  реселлера пока нет.
- **Детект блокировки ручной.** Автоматика (сигнал «нода жива, но хендшейков
  ноль → вероятно, DPI») — в дорожной карте.
- **Ноды работают только с kernel-WireGuard.** AmneziaWG-движок
  (пользовательский демон на основном сервере) на нодах пока не
  поддерживается; на AWG-установках мультинодовость не используется.
- **Статистика Xray-устройств на нодах не собирается** (у Xray нет дешёвого
  per-user API) — «онлайн» корректен только для WG-устройств.
- **В переходный период трафик может задваиваться в счётчиках**: пока
  часть клиентов ещё ходит в старую ноду, обе ноды отчитывают статы одних
  устройств. «Онлайн» и хендшейки корректны, суммарный трафик может быть
  завышен до перекачки конфигов.
- **Нода не поднимает IPv6-егресс сама** — NAT66 настраивается на машине
  ноды так же, как на основной (best-effort).
- Все ноды обслуживают **все** устройства — шардирования по нодам нет (для
  сотен пиров это и не нужно).

## Перенос control plane на новую машину

База и ключи живут в docker-volume `/data`. Перенос = копия volume:

```bash
# на старой машине
docker run --rm -v fibr_fibr-data:/data -v $PWD:/backup alpine \
  tar czf /backup/fibr-data.tar.gz -C /data .
# на новой (после установки Fibr тем же install.sh)
docker compose -f /opt/fibr/install/docker-compose.yml down
docker run --rm -v fibr_fibr-data:/data -v $PWD:/backup alpine \
  sh -c "rm -rf /data/* && tar xzf /backup/fibr-data.tar.gz -C /data"
docker compose -f /opt/fibr/install/docker-compose.yml up -d
```

После переноса в панели смените host у ноды **local** (или `FIBR_WG_HOST`
в `.env`) и перекачайте конфиги — механизм тот же, что и при переключении
нод.

## FAQ

**Зачем нодам свой ключ, если всё равно перекачивать QR?**
Изоляция: утечка ключа одной ноды не даёт подменить остальные. Плюс ноду
можно пересоздать с нуля без инвалидации серверного ключа остальных.

**Можно ли поставить активной ноду, пока старая ещё жива?**
Да, переключение безобидно: туннели не рвутся, меняется только рендер
конфигов. Клиенты со старым конфигом продолжают ходить в старую ноду, пока
она не заблокирована.

**Пользователь успел скачать QR до переключения — что он получит?**
Конфиг старой ноды. Поэтому в Mini App бейдж: «конфиг устарел, скачайте
заново».

**Агент ноды упал — что с клиентами?**
Ничего страшного: WireGuard-интерфейс живёт в ядре, пиры остаются.
Агент нужен для обновления списка и статистики; в панели нода станет
«offline».

**Можно ли цеплять ноды к другому домену/IP без DNS?**
Да, host ноды — просто строка в конфиге клиента; DNS-имя удобнее, но
сырой IP тоже работает.

**Отдаёт ли API токен ноды повторно?**
Нет, только при создании. Потеряли — кнопка «перевыпустить токен» у ноды
(старый мгновенно перестаёт работать).
